# 铝厂余料转炉 · 再生料申报审核页

质检员在签发“最低再生料重量申报”前，用本系统核对称重账能否同时支撑各出货批的
再生料申报。Flask + SQLite + 网络流求解，全部重量按**整数公斤**处理。

## 一、业务规则与建模

1. 账套按炉记录外购**原生料**、外购**再生料**，按出货批记录实称重量，
   并记录余料从哪一炉转往哪一炉、转出多少（实称重量）。
2. 每炉**总进料 = 总出料**（CSV 导入时强制校验，不平衡直接拒收）。
3. 每个出货批最多一张**有效签单**（部分唯一索引保证；撤销记录留历史）。
4. 重核时已签重量照旧；归到各出货批和回炉余料的再生料重量可重新调整。
5. 每炉**再生料进出相等**；每笔出货、每笔转料的再生料重量均以实称重量为上限。
6. 页面给出一套满足全部有效签单的出货/回炉再生料重量；新签或换账无解时
   说明具体瓶颈原因；提交失败则回滚，原账、签单与既有核定结果全部保留。

### 求解模型

带下界的整数网络流（`app/solver.py`，纯标准库实现的 Dinic）：

- `S → 炉`：容量为该炉外购再生料；
- `炉 → 出货批`：容量为批实称重量，**下界为有效签单下限**；
- `出货批 → T`：容量同为批实称重量；
- `炉 → 炉`：余料转料，容量为转料实称重量；
- 加 `T → S` 无穷边与超级源/汇，把带下界可行流转为最大流判定；
  可行后再跑一次 `S → T` 最大流，使出货承载尽量大。
- 容量均为整数，Dinic 保证得到整数解；无解时用残量网络最小割定位
  饱和的出货/转料通道与缺料炉，生成中文原因。

## 二、CSV 格式

UTF-8、首行表头，列固定为：

| 列 | 说明 |
|---|---|
| `record_type` | `furnace` / `batch` / `transfer` |
| `furnace` | 炉号（transfer 时为源炉） |
| `ref` | batch=出货批号；transfer=目标炉；furnace 留空 |
| `primary_kg` | 仅 furnace：外购原生料（留空按 0） |
| `recycled_kg` | 仅 furnace：外购再生料（留空按 0） |
| `weight_kg` | batch/transfer 的实称重量 |

示例见 `data/sample_ledger.csv`。

## 三、运行

### Docker Compose（交付方式）

```bash
docker compose up --build
# 打开 http://localhost:8000
```

SQLite 数据库存放在命名卷 `audit-data`（容器内 `/data/audit.db`），
容器重建数据不丢；生产环境请修改 `AUDIT_SECRET_KEY`。

### 本地直接运行

```bash
python -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt
python wsgi.py            # 开发服务器，:8000
# 或
gunicorn --bind 0.0.0.0:8000 wsgi:app
```

## 四、页面操作

1. **上传 CSV**：首次直接导入；换账须勾选“替换当前账套”。导入即核定。
2. **分炉补报（暂存）**：在审核页选择现行账套中的炉号，沿用同一套 CSV 列上传该炉
   完整的外购、出货批与进出转料明细。补报先暂存、不改动原账；同一账套内同炉重传
   以新文件整份为准，可随时删除。旧账套的补报只绑定原账套，不会串到新账套。
3. **合账试算**：进入试算页（只读、不写库）执行三项核对——
   - 转料双向核对：转料有变动时两端炉都要补报；按炉对逐方向核对笔数与每笔重量，
     缺报或不符直接列出炉对与差异；
   - 合并账物料平衡：未补报炉沿用原账，补报炉以补报为准，按既有规则复核
     每炉总进料＝总出料；
   - 全部有效签单重核：用求解器在合并账上预跑，给出试算核定重量或无解瓶颈。
4. **合账提交**：试算页签发依据令牌（现行账套 + 补报指纹 + 有效签单指纹）。
   试算期间其他人仍可补报、签撤或换账；提交时重新取数比对，任一依据不同即退回
   本次合账。核对与重核全部通过后，**新账套与核定结果在同一事务内一同生效**，
   失败则整笔回滚，补报、签单与已生效数据全部保留；原账套及其补报保留可查。
5. **核定结论**：展示可行方案或无解瓶颈；可随时“重新核定”。
6. **炉次账**：展示各炉进料/出料与平衡结果。
7. **出货批**：每行可签发（填正整数、不超过实称）或撤销签单，
   并显示该批核定再生料重量。
8. **余料转炉**：每笔转料的实称上限与核定再生料重量。
9. **签单台账**：有效/已撤销全部留痕。
10. **操作日志**：成功与失败（回滚）事件均记录，含补报上传/删除与合账提交。

### 分炉补报 CSV 口径

与整账 CSV 完全相同的 6 列表头，单文件只描述一座炉：

- 恰好一条 `furnace` 行，炉号必须等于审核页所选炉号；
- `batch` 行归属炉必须是该炉；`transfer` 行源或目标至少一端是该炉
  （即该炉**进出两侧**转料都要报齐），对端炉号须在现行账套内；
- 强制校验该炉总进料（外购 + 转入）＝总出料（出货批 + 转出），不平衡直接拒收。

示例：`data/supplement_F1.csv`、`data/supplement_F2.csv`、`data/supplement_F3.csv`。

## 六、目录结构

```
app/
  solver.py     带下界整数网络流（Dinic）与无解原因解释
  csvutil.py    整账/分炉补报 CSV 解析与物料平衡校验
  merge.py      合账引擎：转料双向核对、合并建账、平衡复核、试算依据指纹
  db.py         SQLite 建表、事务、签单/核定/补报持久化
  web.py        Flask 路由（所有写操作单事务，先试算后提交）
  templates/    审核页与合账试算页
  static/       样式
tests/          求解器、CSV 与端到端测试
data/           示例整账与分炉补报 CSV
Dockerfile / docker-compose.yml / wsgi.py / requirements.txt
```
